## 执行顺序与入口

1. 完成需求、Blueprint、ADR、接口、权限、运行策略、验收数据和测试准备。可生成待审测试，不生成应用实现。
2. 零费用mock验证OpenCode配置和权限，验证所有请求的输出限制、重试和费用边界。准备阶段最多1美元、最多12次生成请求，均计入开发分账。
3. 检查点1：用户对具体需求、架构、执行计划、测试计划及测试内容作出真实批准；用户亲自建立Human-only规则。记录文件哈希和真实时序。
4. 第一波：契约、证据、门禁、审阅发布闭环；固定响应先验证。
5. 第二波：同一个claim-turn适配器接入多空及三个风险角色；统一预算客户端覆盖工具、结构化回退、反思和重试；加入评估命令。
6. 检查点2：用户审阅实际安全diff、ADR、离线证据和实验协议，批准业务pilot及正式实验。
7. 三个股票任务各两次、两组共12次正式运行；失败全部保留。唯一学生标注并至少间隔24小时复核，整理局限。
8. 检查点3：最终代码、评估、报告、交付包审阅；真实批准一个演示产物hash。

常规三个人审关卡不构成未来变更的空白批准。安全边界、已批准测试或模型/端点发生实质变化，应先停止受影响部分，呈现具体差异并重新取得批准。

## 每轮OpenCode工作

为单一模块下发任务：目标需求、允许路径、禁止路径、接口、已批准测试、退出条件。禁止宽泛“完成整个项目”任务。

隔离XDG数据/缓存/状态/配置；显式指定课程provider、模型、角色、`--standalone`及JSON事件输出，不使用`--auto`。真实课程密钥仅由本机传输进程读取，OpenCode只得到本地无外部效用token。默认禁止MCP、插件、其他provider和任意shell。

至少保留五个真实session：需求/架构/测试准备；边界闭环；辩论与预算集成；验证返工；交付检查。保留原始事件，使用`opencode session export SESSION_ID --sanitize`导出，另做脱敏复查。用户批准与本聊天的真实事件关联，Codex转交不得标成用户亲自输入。
